## 七、查清了一个「我造成的数据污染」（重要）

**Visits/Visitors = 8.8 这个异常，我找到了确切原因。**

排查过程：
1. 检查 Playwright MCP 配置（`~/.workbuddy/mcp.json`）→ **没有 `--isolated` 参数**
2. 实测我的测试浏览器里 `localStorage` 保留了 `imd.locale`（我几天前设置的值）
   → **证明这个浏览器 profile 是持久化的**
3. 实测 `window.umami` = object、追踪脚本已加载 → **我的测试确实被统计了**

**结论**：Playwright MCP 使用持久化浏览器身份，所以我这一周的几十次自动化测试
**共用同一个访客 ID** —— 表现为「1 个访客产生了大量访问」，这正是 Visits/Visitors 虚高的来源。

同时它还贡献了相当一部分浏览量（每次测试加载 5-15 个页面），
且**我测试最密集的 9/17-9/18 与 9/20，恰好对应数据的高峰与回升点**。

**这是我的问题，不是网站的问题。** 修复方式不需要改站点——我在测试时屏蔽分析请求即可
（Playwright 侧拦截 `cloud.umami.is` 的请求），已记入 `web-qa-scan` 技能，以后自动化测试不再计入。

> 历史污染无法追溯清除。但从下一个数据窗口起，这部分噪音会消失。

### 优先级（按投入产出比）

**🔴 P0：把首页流量导向内页**

数据已经指明：**你有 3,060 条 URL，但 78% 的访客只看首页。**
不是内容不够，是「进去之后没有路」。这是当前最大的、且完全由我们可控的漏损点。

**🔴 P0：继续发外链（且优先英文渠道）**

自然搜索已经起量、Bing 表现最好、海外占 46% —— 证明方向对了。
外链仍是唯一能加速这个进程的动作，且现在有了「Bing 已经收录」的正反馈。

**🟡 P1：等一个干净窗口再读数**

我的测试污染已从源头消除，预览噪音已堵。**下一个 24 小时才是真正干净的第一个窗口**，
届时 Bounce / Visits每访客 / Organic search 这三个数才值得当基线。

**🟢 P2：CI 日志里的预览 token 脱敏**（建议与下次自然部署合并，避免额外部署）
